这篇记录 DeepSeek-V4.1-Flash 在一台 8 卡 H20 上的部署：上下文开到 512K 的依据，选 vLLM 不选 SGLang 的原因，调参的过程，压测方法，以及上线和回滚。数字全部来自 2026 年 9 月到 10 月的测试记录，每个数字都写明口径。没测过的地方，我直接写没测。

最终线上配置是 vLLM v0.32.0，TP8 加 EP8，`max-model-len` 为 524288，DSpark 投机解码取 3 个草稿 token，KV cache 用 FP8，Engram 表放主机内存，`max-num-seqs` 128，`max-num-batched-tokens` 4096，显存比例 0.90。在这套配置下，输入 256、输出 128、并发 32 的输出吞吐约 997 tok/s，输入 1K、输出 1K、并发 100 约 1692 tok/s。

## 背景与目标

在这之前，同类业务跑在另一台 H20 上的 V4-Flash-0731，用 SGLang v0.5.19，TP4 占 4 张卡，256K 上下文。V4.1-Flash 和它的差别比换个版本号大得多：

| 项 | V4-Flash-0731 | V4.1-Flash |
|---|---|---|
| 权重 | 约 156G，48 个 shard | 475.3 GiB，48 个 shard |
| 引擎 | SGLang v0.5.19（W4A8） | vLLM，先用 0909 专用镜像，后换 v0.32.0 |
| 并行 | TP4，占 4 卡 | TP8 加 EP8，独占 8 卡 |
| 投机解码 | DSPARK，6 个草稿 token | DSpark，3 个草稿 token |
| 上下文 | 256K | 512K |

目标有三条。第一，对外服务名不变，网关按主机区分两台机器。第二，上下文要能到 512K。第三，相对已有基线，目标并发的输出吞吐下降不超过 10%，TTFT P50 劣化不超过 10%，P95 不超过 15%，成功率 100%。这是我在评估方案里写的门槛，后面所有“淘汰”都是按它判的。

时间线很短：9 月 11 日开始在 vLLM 上调参，9 月 13 日用 0909 版权重和专用镜像上线，10 月 18 日开始评估 1017 版权重加官方 v0.32.0 镜像，10 月 20 日转正。

## 硬件与约束

| 项 | 值 |
|---|---|
| GPU | 8 × H20，SM90，每卡约 97.9 GiB |
| 驱动 / CUDA | 580.173.02 / 13.0 |
| 权重 | 475.3 GiB，48 shard（1017 与 0909 的 config、tokenizer 逐字节相同，只换了权重） |

这套约束里有四条直接决定了后面的选择。

一个实例要占满 8 卡。评估阶段试过两个 TP4 实例各占 4 卡，能启动，但单实例的 KV cache 只有 1,615,139 token，按 512K 算满长请求只能并发 3.08 路；TP8 加 EP8 是 17,594,168 token，33.56 路。

FP4 的 indexer 缓存用不了。把它设成 FP4 会启动失败：vLLM 把这条路径解析成 MXFP4，要求 Blackwell 的 SM100/SM103，H20 是 SM90。只能用 FP8。

经典 MTP 用不了。V4.1 的 checkpoint 没有 MTP 需要的权重，vLLM 明确要求用 `dspark`。

单机独占还带来一个运维上的后果：评估新版本必须停掉线上容器。评估 1017 那次，我先让网关把流量切走，才在原端口上跑测试。

H20 的特点，我只写测出来的。和一份 H800 上同场景的数据对比，H20 的单并发还不错，并发一高就差得很快（具体比例在后面的结果一节）。资料里没有做 profiling，所以“高并发时算力成为瓶颈”只是我对这条曲线的解读，不是实测结论。显存倒是宽裕：Engram 表（约 189 GiB，8 卡合计）可以整个挪到主机内存里，下一节会讲。

## 上下文长度怎么取舍

先说一件事：我手上没有线上请求长度的分布统计。所以上下文上限不是按分布定的，是按两个问题定的：显存能撑多少路，以及长请求要付多大代价。

### KV cache 容量

9 月 12 日我在同一镜像、同一组参数（TP8、EP8、DSpark3、FP8 KV、`max-num-seqs` 128、`max-num-batched-tokens` 4096、显存比例 0.90）下，只改 `max-model-len` 和 Engram 的位置，看 vLLM 启动时报告的 KV 容量：

| max-model-len | Engram 位置 | KV cache（token） | 满长请求并发估计 |
|---|---|---:|---:|
| 256K | 主机内存 | 15,557,833 | 59.35 |
| 256K | GPU | 6,393,940 | 24.39 |
| 1M | 主机内存 | 16,510,091 | 15.75 |
| 1M | GPU | 4,237,386 | 4.04 |

“满长并发估计”是 vLLM 用 KV 容量除以上限算出来的，不是压测结果。

Engram 放 GPU 每卡多占 23.61 GiB，8 卡合计约 189 GiB，256K 下 KV 容量降到主机内存方案的约 41%。收益呢？C1 到 C16 吞吐差别在 1% 以内，C32 低 7.6%（单轮，不算稳定差异），240K 输入、C1 的 TTFT 是 56.1 秒对 56.6 秒。多花的显存没换来任何速度，所以 Engram 一直放主机内存。

### 1M 能跑，但不能用

同一组测试里，两种 Engram 放置方式都成功完成了一个 1,000,000 token 输入、16 token 输出的请求，首 token 要 460 秒左右。这说明容量上走得通，交互场景用不了。1M 满长的并发估计只有 15.75 路，我没有把它当上线选项。

### 为什么停在 512K

最终取 524288，对应的 KV 容量是 17,594,168 token（1017 加 v0.32.0），满长并发估计 33.56 路。在这个长度上，1017 加 v0.32.0 的长输入预填充数据如下（每档 10 个请求，输出 16 token，输入长度与目标精确一致，对比的是 0909 加旧镜像）：

| 输入 / 并发 | TTFT P50（1017 对 0909） | 预填充吞吐 tok/s（1017 对 0909） |
|---|---|---|
| 64K，C1 / C2 / C4 | 5.5 / 8.9 / 19.4 s 对 14.3 / 22.7 / 49.9 s | 12017 / 7376 / 3379 对 4596 / 2882 / 1313 |
| 128K，C1 / C2 / C4 | 12.2 / 21.7 / 46.6 s 对 31.0 / 55.0 / 116.5 s | 10703 / 6042 / 2812 对 4234 / 2385 / 1125 |
| 240K，C1 / C2 | 25.1 / 46.7 s 对 64.6 / 120.7 s | 9800 / 5259 对 3807 / 2037 |

预填充吞吐平均提升约 150% 到 160%，TTFT 和 E2E 下降约 60%。测试中没有 OOM、没有重启，GPU 显存峰值约 93.3 GiB 每卡。

这里有两个必须说明的缺口。其一，这轮长上下文测试是部分完成的：网关切回后出现了业务流量，我在 18:35 停了测试，240K 的 C4、262K、393K、524272 边界档和长短混合都没测。其二，262K、393K 边界和 1 小时 C16 soak 是在 0909 版本上测的，通过了；1017 没有重做。

### 上限是总预算

在 0909 版本上，输入 524272、输出 16 的请求返回了 HTTP 400。日志里没有保留服务端的错误内容，所以拒绝原因我没有确认，也不知道真正可用的最大输入是多少。我的做法是把 524288 当成提示词、聊天模板和输出的总预算，业务请求留足余量。这条已经写进了生产说明。

### 长请求要隔离

长输入的代价不止是自己慢。09 月 14 日的一次混合测试：一个 240K 请求，叠加 300 个并发 16 的短请求，V4.1（0909）上短请求的 TTFT P95 是 62.4 秒，同一场景下 V4-0731 是 41.0 秒；中位数倒是 219 毫秒对 235 毫秒，差别全在尾部。17.4K 输入的矩阵里也一样：并发 100 时 TTFT P99 约 380 秒。结论是长请求要单独路由并限并发，不能和短请求共用一个高并发池。

## 引擎与关键参数

### vLLM 对 SGLang

我用 SGLang 测了三个镜像，参数参照它官方食谱里 Hopper 的 TP8·EP8 条目（Marlin MoE、DSPARK block 5、chunked prefill 4096），再按本机对齐 512K 和 Engram 主机内存。结果如下（SGLang 取最好的镜像，除第二行标注的外，数字都是输出 tok/s）：

| 场景 | vLLM（1017 加 v0.32.0） | SGLang（nightly 1014） | SGLang（nightly 0922，显存比例 0.80） |
|---|---:|---:|---:|
| 256/128，C32 热 | 1122.8 | 617.4 | 124.5 |
| 1K/1K，C1 | 214.2 | 200.2 | 92.6 |
| 1K/1K，C10 | 862.4 | 607.7 | 154.0 |
| 1K/1K，C50 | 1439.5 | 848.2 | 163.5 |
| 1K/1K，C100 | 1666.9 | 846.1 | 180.8 |
| 17.4K/1K，C1 | 153.2 | 119.3 | 63.5 |
| 17.4K/1K，C10 | 367.6 | 174.0 | 83.2 |

SGLang 最好的镜像在单并发时差距不大，并发一上去只有 vLLM 的约一半。另外有几件事一并记下：

- 0922 镜像按默认显存比例 0.85 起服务，跑到长上下文时 CUDA 分配器连 20 MiB 都映射不出来，OOM 了；降到 0.80 才跑完。
- 0910 的开发镜像在 Engram 的 per_rank 布局上断言失败，改成 shared 布局才启动。
- SGLang 的首次启动要 16 到 30 分钟，vLLM 同配置约 8 到 10 分钟。
- SGLang 的推理字段叫 `reasoning_content`，vLLM 叫 `reasoning`，上线要网关兼容。

公平性上要交代：SGLang 这边是按食谱默认参数跑的，我没有像对 vLLM 那样逐项调。0922 和 1014 两个镜像的数据出来后，我中止了 0910 镜像的评估，因为吞吐差距已经大到调参很难补上。这是一个工程决定，只针对 V4.1 在这台机器上的表现，不是对两个引擎的一般性结论；V4-0731 线上用的就是 SGLang。

### 最终启动命令

```bash title="start-v41.sh"
docker run -d \
  --name dsflash-v41-1017 \
  --restart unless-stopped \
  --network host --ipc host --shm-size 64g --gpus all \
  --security-opt label=disable \
  -e VLLM_WORKER_MULTIPROC_METHOD=spawn \
  -e VLLM_ENGINE_READY_TIMEOUT_S=3600 \
  -v $DATA_ROOT/cache:/root/.cache \
  -v /models:/models:ro \
  -v $DATA_ROOT/logs:/logs \
  vllm/vllm-openai:v0.32.0 \
  /models/DeepSeek-V4.1-Flash-1017 \
  --served-model-name deepseek-flash \
  --port $PORT \
  --tensor-parallel-size 8 --enable-expert-parallel \
  --max-model-len 524288 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 128 --max-num-batched-tokens 4096 \
  --kv-cache-dtype fp8 \
  --engram-config '{"cpu_offload":true}' \
  --attention-config '{"indexer_kv_dtype":"fp8"}' \
  --enable-prefix-caching \
  --speculative-config '{"method":"dspark","num_speculative_tokens":3,"draft_sample_method":"greedy"}' \
  --reasoning-parser deepseek_v41 \
  --enable-auto-tool-choice --tool-call-parser deepseek_v41 \
  --trust-remote-code --tokenizer-mode deepseek_v41
```

`VLLM_ENGINE_READY_TIMEOUT_S` 设成 3600 秒，给首次启动留足时间：新配置第一次启动要做 JIT 编译和 CUDA Graph 捕获，实测在 13 到 29 分钟之间，之后同配置重启约 7.5 到 10 分钟。

### 每个参数是怎么定的

TP8 加 EP8。纯 TP8 时每卡权重约 49.7 GiB，打开专家并行后降到约 38.1 GiB，KV cache 从约 776 万 token 升到约 1113 万。同时我把 `max-num-seqs` 从 16 提到 128，C32 的输出吞吐从 514 升到 737 tok/s（三轮均值）。这两个改动是一起做的，没有单独拆开，所以不能把 43% 全算给专家并行。

DSpark 草稿数取 3。9 月 12 日在 EP8 下只改这一项：C32 三轮均值，草稿 5 个是 735.6 tok/s，草稿 3 个是 814.5 tok/s，高 10.7%。日志里的平均接受长度在 2.0 到 2.2，草稿接受率 34% 到 41%，草稿 5 个时是 23.6% 到 25.0%。10 月在 1017 加 v0.32.0 上又试了 2、4、5：草稿 2 的吞吐不低于 3，但 TTFT P95 最多恶化 94%；4 和 5 的吞吐更差。官方食谱里的 probabilistic/synthetic acceptance 配置是 benchmark 专用的，我没有采用。

`max-num-batched-tokens` 取 4096。vLLM 里它是每个调度步的 token 预算，预填充按这个预算切块。4096 比 8192 在同一个 256K 配置下让 KV 容量从约 1113 万升到约 1553 万；在 512K 的 1017 配置上，8192 的 KV 容量是 13,916,531，比 4096 少 20.9%。吞吐上我测了两次：9 月 20 日把 `max-num-seqs`/`max-num-batched-tokens` 同时调到 256/8192，1K/1K 的输出吞吐只提升 0% 到 2.4%；10 月 20 日 300 请求乘 3 轮的正式对比，8192 在 C16、C32、C100 都在噪声内，只有 17.4K 输入 C10 快了 3.6%，而 1K/1K C50 的 E2E P95 从 59.8 秒变成 71.2 秒。结论是不切换。启动日志里有一条提示，说 4096 的调度 token 数和投机解码槽位的配置可能影响性能。实测里提高到 8192 并没有更好的结果，所以我没有为这条提示改参数。

`gpu-memory-utilization` 保持 0.90。调到 0.93 后 KV 容量从 17,594,168 升到 18,929,800（约 7.6%），但吞吐在噪声内（C32 热 1132.5 对 1122.8，C100 1676.2 对 1666.9）。而长上下文测试里每卡峰值已经到约 93.3 GiB，卡上一共约 97.9 GiB，剩下的余量不值得为 7.6% 的容量去换。SGLang 0922 镜像在 0.85 下 OOM 的例子也说明这个余量是真的会被用到。

FP8 KV 和 FP8 indexer KV 是硬约束：FP4 在 H20 上启动失败（前面说过）。MoE 用 vLLM 默认的 Marlin，换成 FlashInfer Cutlass 更慢（TP8 实验里 C1 到 C32 分别是 79.97、247.46、473.15、485.37 tok/s，同一组测试里默认方案是 87.44、273.12、495.83、514.26）。

最后是一串试过但没留下的东西：TP8 不开专家并行、DSpark5 和 10、Rust frontend、Marlin atomic add、FlashInfer Cutlass、FP4 indexer、Engram 放 GPU。Rust frontend 在 `max-num-seqs` 256 下 C32 是 590.8 tok/s，低并发 TTFT 更好、吞吐不如经典前端；Marlin atomic add 只改善了 C1 和 C4。

`--enable-prefix-caching` 是开着的，但我所有压测用的都是互不重复的随机输入，所以前缀缓存在线上能带来多少收益，我没有测。

## 压测方法

### 工具与口径

所有测试，不管打的是 vLLM 还是 SGLang，客户端都是同一个镜像里的 SGLang `bench_serving`，后端选 `vllm-chat`，数据集 `random-ids`（本地生成，不依赖外部下载）。固定长度，`--random-range-ratio 1.0`，请求体里 `max_tokens` 等于 `min_tokens`，关闭 thinking：

```bash title="quick-bench.sh"
python3 -m sglang.bench_serving \
  --backend vllm-chat --base-url http://localhost:$PORT \
  --model /models/DeepSeek-V4.1-Flash-1017 --served-model-name deepseek-flash \
  --dataset-name random-ids --random-input-len 256 --random-output-len 128 \
  --random-range-ratio 1.0 --num-prompts 300 --request-rate inf --max-concurrency 32 \
  --warmup-requests 0 --seed $SEED \
  --extra-request-body '{"max_tokens":128,"min_tokens":128,"chat_template_kwargs":{"thinking":false}}' \
  --output-file out.jsonl --output-details
```

几条规则是被踩过坑之后加上的：

- 固定长度预检：正式开跑前先发一个请求，确认输入正好 256、输出正好 128 token，不满足就停。`random-range-ratio=0` 在 SGLang 里表示长度在 1 到目标值之间随机，不能用来做固定长度对比。
- 每档校验 `completed` 等于请求数、`output_lens` 全部等于目标值、`errors` 为空，任何一项不满足这一档标 `valid=false`，不进结论。
- 吞吐按实际生成的 token 数算，不按目标长度。
- 冷缓存：vLLM 没有可移植的清缓存接口，我把“换种子、无前缀复用”定义为冷缓存，报告里注明。
- 预热：CUDA Graph 和 JIT 的首轮不计入。9 月 12 日的 DSpark3 复测里，首轮 C16 的 TTFT P95 是 5.13 秒，之后三轮是 0.40 到 0.48 秒，所以首轮的尾延迟不能代表稳态。

### 测试矩阵

| 名称 | 输入 / 输出 | 并发 | 每档请求数 | 用途 |
|---|---|---|---|---|
| quick | 256 / 128 | C1、C4、C16、C32，冷热各一组 | 100（正式：300 × 3 轮） | 参数筛选的主指标 |
| A | 1K / 1K | C1、C10、C50、C100 | 100（正式：300 × 3 轮） | 高并发扩展性 |
| B | 8K / 8K | C1、C10、C50、C100 | 100 | 与 H800 数据对照 |
| C | 17.4K / 1K | C1、C10（对照时加 C50、C100） | 100（正式：100 × 2 轮） | 长输入 |
| 长上下文 | 64K、128K、240K，输出 16 | C1、C2、C4 | 10 | 预填充和 TTFT |
| 自然回答 | 28 条固定 prompt，覆盖代码、数学、中文问答、写作、工具调用 | C1、C16 | 3 轮 | goodput、输出长度、DSpark 接受率 |

另外每个候选都会跑 API 兼容矩阵和冒烟：`tool_choice=auto`、思考开关、流式 usage。

### 两阶段筛选

因为是单机 8 卡，A/B 只能串行。我把测试分成两层：

1. 第一层是单轮、每档 100 个请求的快速筛选，11 个配置串行跑，前后十几个小时。通过的门槛是 100% 成功，加上 TTFT P95 相对基线的劣化不超过 15%。
2. 入围的 1 到 2 个再做 300 请求乘 3 轮的正式对比，每轮种子不同，两个配置之间用同样的种子。

原生产（0909 加旧镜像）的基线，是网关把它切走之后在同一个口径下补测的单轮数据。这是整套评估里最弱的一环，下面解读结果时会再提到。

踩过的口径坑也要记下来：9 月 14 日那次 V4 对 V4.1 的短请求矩阵，因为种子（形如 20260914101）超过了 NumPy 接受的 32 位范围，客户端在发请求之前就抛了 ValueError，整个短请求矩阵没有有效数据；长上下文部分是好的。同一次测试的 soak 脚本还复用了已经过期的时间预算，循环计数被空转的迭代撑大，不能当成功次数。这两处都让我只保留了有效的部分，没有硬凑结论。

## 结果与解读

### 正式口径：1017 加 v0.32.0 对原生产

1017 加 v0.32.0 的数字是 3 轮均值 ± 轮间标准差，每轮 300 请求（17.4K 那一行是 100 请求乘 2 轮），900/900（17.4K 是 200/200）全部成功。原生产是筛选阶段的单轮数据。

| 场景 | 1017 加 v0.32.0 | 原生产 0909 | 提升 |
|---|---:|---:|---:|
| 256/128，C16，热 | 753.5 ± 11.1 | 716.9 | +5% |
| 256/128，C32，热 | 996.5 ± 7.2 | 902.6 | +10% |
| 1K/1K，C50 | 1402.5 ± 30.3 | 1199.9 | +17% |
| 1K/1K，C100 | 1692.1 ± 15.3 | 1340.0 | +26% |
| 17.4K/1K，C10 | 389.8 ± 1.6 | 216.6 | +80% |

单位是输出 tok/s。同一轮的延迟：

| 场景 | TTFT P50 | TTFT P95 | TPOT P50 | E2E P95 |
|---|---:|---:|---:|---:|
| 256/128，C16 | 169.5 ms | 1135.8 ms | 19.3 ms | 3.68 s |
| 256/128，C32 | 263.4 ms | 683.7 ms | 29.6 ms | 4.82 s |

| 17.4K/1K，C10 | 1.95 s | 7.22 s | 21.1 ms | 40.3 s |

C16 的 TTFT P95 带着约 1.4 秒的轮间标准差，说明三轮里有一轮仍出现了尾部尖峰。TPOT P50 换成单用户解码速度，C32 约 34 tok/s，C100 约 21 tok/s。

提升有两条需要打折。一是原生产只有单轮基线：筛选阶段同口径的单轮提升是 C16 +13%、C32 +24%，正式口径只有 +5%、+10%，差别来自 100 请求和 300 请求的口径不同，所以短请求的提升我更相信正式的数字，而基线本身没在 300 乘 3 的口径下重测，短请求两档的提升可能被低估。二是 TTFT 的尾部同时下降：C32 的 TTFT P95 从 1.29 秒降到 0.83 秒，17.4K 的 C10 从 17.6 秒降到 7.2 秒。

### 提升来自哪里

筛选阶段我把权重和镜像拆开测过（单轮，输出 tok/s）：

| 配置 | 256/128 C32 热 | 1K/1K C50 | 1K/1K C100 | 17.4K/1K C10 |
|---|---:|---:|---:|---:|
| 0909 权重加旧镜像（原生产） | 902.6 | 1199.9 | 1340.0 | 216.6 |
| 1017 权重加旧镜像 | 900.4 | 1136.9 | 1304.2 | 207.6 |
| 0909 权重加 v0.32.0 | 1110.9 | 1125.0 | 1397.6 | 346.6 |
| 1017 权重加 v0.32.0 | 1122.8 | 1439.5 | 1666.9 | 367.6 |

只换权重或只换镜像，C50 和 C100 都没有稳定收益（0909 权重加 v0.32.0 的 C50 反而低了 6%）。两个一起换，C50 和 C100 才拉开 20% 以上。所以报告里写“提升来自 v0.32.0 运行时”只对了一半：短请求和长输入的提升确实主要来自新镜像（0909 加 v0.32.0 的 C32 和 17.4K 已经有 +23% 和 +60%），高并发的提升则要两者配合。这一条我没有做进一步归因。

### 自然回答与 API

固定长度的随机输入测的是解码吞吐，真实回答的长度分布不同。28 条 prompt 乘 3 轮、C16、关闭思考时，1017 加 v0.32.0 每秒完成 1.41 个请求，原生产（单轮）是 1.12；开启思考时平均输出约 1400 到 1600 token。这个口径和随机输入吞吐不同，我没有把它并进上面的排名。API 冒烟（关闭思考、默认思考、`tool_choice=auto` 工具调用）全部通过。

### 与 H800 和上一代的差距

用同一个 SGLang `bench_serving` 在 0909 版本上复现了一份 H800 报告的场景，每档 100 请求。H20 的输出吞吐占 H800 的比例：

| 场景 | C1 | C10 | C50 | C100 |
|---|---:|---:|---:|---:|
| A：1K/1K | 84% | 57% | 39% | 33% |
| B：8K/8K | 53% | 44% | 39% | 31% |
| C：17.4K/1K | 52% | 36% | 29% | 27% |

H800 那边的参数和客户端细节不完全可见，这个比例只当容量趋势看。曲线的形状是：单并发还行，并发越高差得越多。C 场景从 C10 到 C100 输出吞吐几乎不再增长（215 到 245 tok/s），100 个 17.4K 请求合计约 174 万输入 token，按整机约 4,400 tok/s 的总吞吐算，要排 6 分半钟，对得上我看到的 380 秒左右的 P99 TTFT。

和 V4-0731 的对比只有 9 月 14 日（0909）的数据：64K 到 240K 的单档测试里，V4.1 的总 token 吞吐是 V4-0731 的 55% 到 66%，TTFT 中位数是 1.5 到 3.1 倍；240K、C4 时 TTFT 中位数 247 秒对 84 秒。1017 加 v0.32.0 把长输入预填充提高了约 150%，但我没有在同一口径下重新对比 V4-0731，所以这一段追平了多少，我不下结论。

## 上线配置与回滚

### 部署脚本的守卫

部署脚本默认 dry-run，加 `--apply` 才执行。它在动手之前检查五件事，任何一条不满足就拒绝：

```bash title="deploy-v41.sh（节选）"
# 权重分片齐全
test -f "$MODEL/model-00048-of-00048.safetensors"
# 镜像 ID 和评估时一致
[[ "$(docker image inspect -f '{{.Id}}' "$IMAGE")" == sha256:bd8a5d7a8774* ]]
# 新容器名没被占用
! docker container inspect "$PROD_CONTAINER" >/dev/null 2>&1
# 旧生产容器没在运行，要先显式停掉
! docker inspect -f '{{.State.Running}}' "$OLD_PROD" 2>/dev/null | grep -qx true
# 服务端口上没有在途请求
busy=$(curl -s --max-time 5 "http://localhost:$PORT/metrics" |
  awk '/^vllm:num_requests_(running|waiting)\{/ {s+=$NF} END{print s+0}')
[[ "$busy" == "0" ]]
```

通过之后的动作是：保存测试容器的 `docker inspect`，用 `docker stop --time 120` 停掉测试容器（只 stop 不 rm），确认端口已释放，再启动生产容器，最后把新容器的 `inspect` 快照存到数据盘。重启策略是 `unless-stopped`。

### 回滚预案

旧生产容器（0909 权重，旧镜像）在切换后保持 Exited 状态，没有删除，启动参数留了一份脚本。回滚就是两条命令：

```bash title="rollback.sh"
docker stop dsflash-v41-1017 && docker start dsflash-v41-0909
```

两个容器都要 8 张卡，不能同时运行，所以顺序必须是先停后启。按同镜像候选的记录，启动到健康大约 8 到 10 分钟；旧容器本身的回滚耗时没有实测过，也没有演练记录。回滚触发条件（OOM、健康检查失败、参数不兼容）我在评估方案里写过，但没有为线上写成自动化。

### 网关要处理的接口差异

这些是上线前必须告诉调用方的，来自 9 月 13 日和 10 月 20 日的兼容性测试：

- 不传 `reasoning_effort` 时服务端默认 75（v0.32 实测），不是我最初假设的 50。如果业务依赖旧的默认值，要显式指定。
- 顶层 `reasoning_effort` 只接受 `none`、`low`、`high`、`xhigh`、`max`。`minimal`、`medium`、`ultra` 和数值都会返回 400，网关需要把 `minimal`、`medium`、`ultra` 分别映射到 `low`、`high`、`max`。
- 工具调用时 `finish_reason` 是 `stop`，不是 `tool_calls`，网关应该以 `message.tool_calls` 判断。
- 不传 `max_tokens` 时没有按思考档位给默认值，建议网关显式传。
- 推理内容在 `reasoning` 字段，不是 `reasoning_content`。
- 上下文上限是 524288，旧版是 262144，两台机器的模型 ID 相同，靠网关按主机区分。

## 几条能复用的经验

1. 先算 KV 预算再定上下文。同样是 `max-model-len`，Engram 放主机内存和放 GPU 差了 2.4 倍的 KV 容量；`max-num-batched-tokens` 从 4096 提到 8192 又吃掉 20.9% 的容量。上限不是越大越好，要和“满长请求能并发几路”一起看。
2. 先固化口径再比较。固定长度预检、有效性校验、种子范围检查，每一项都是被一次作废的数据逼出来的。
3. 筛选用单轮，结论用多轮。同一个配置，100 请求单轮显示 C32 提升 24%，300 请求三轮只剩 10%。
4. 一次只换一个变量，并且要把交互拆开测。权重和镜像单独换都不见效，一起换才有 20% 以上的高并发收益；只看一个对照，会得到错误的归因。
5. 保留旧容器，只 stop 不删。单机独占 8 卡意味着评估和回滚都要停掉线上，旧容器和 `inspect` 快照是整个预案里最便宜的保险。
6. 在 H20 上，高并发和长输入不要指望线性扩展。长请求单独路由并限并发，比调任何一个启动参数都有用。
7. 否决清单也要记。DSpark5 和 10、Rust frontend、Marlin atomic、FlashInfer Cutlass、Engram 放 GPU，每一项都花了几小时，写下“试过、没用、原因是什么”，下次就不用再试。

还没做的事也列一下：1017 版本的 262K 以上边界和 soak，长短混合负载在 1017 上的复测，一个在 300 乘 3 口径下重测的原生产基线，以及线上真实请求长度的分布统计。其中最后一项会直接影响 512K 这个上限是否合适。
